# 需求质量检查命令

两种检查的分工：
- **质量门禁（--gate）** = "文档写得好不好？"——阶段完成时检查文档质量
- **验收清单（--verify）** = "功能做对了没有？"——实现完成后人工逐项确认

## 用法

```bash
/crs:req-quality <req-id> [--gate <1-4>] [--verify <design|implementation|deployment>]
```

`--gate`/`--verify` 缺省时自动推断当前阶段。

## 质量门禁（通过条件：自动检查全过 + ≥80% 手动确认）

### Gate 1 设计完成（设计文档完成后）

- 自动：无占位符（TBD/TODO）、无矛盾、决策理由完整、架构完整、错误处理覆盖
- 手动：决策都有理由；架构图清晰；错误处理覆盖主场景；接口明确；数据流完整

### Gate 2 测试策略完成（测试计划生成后）

- 自动：测试类型覆盖 ≥3 种、关键路径有测试、性能指标已定义、安全风险已识别
- 手动：场景覆盖业务需求；测试数据充分；验收标准明确；测试环境清晰

### Gate 3 实施计划完成（计划生成后）

- 自动：任务可执行、依赖清晰、估算合理、风险预案完整
- 手动：分解粒度合适；资源分配合理；里程碑明确；相关方确认

### Gate 4 变更完成（变更处理后）

- 自动：影响评估完整、文档已更新、测试已调整、干系人已通知
- 手动：变更理由充分；影响范围准确；方案可行；回滚计划就绪

## 验收清单（--verify）

**设计验证（design）——开始实现前**
- [ ] 理解用户需求与业务价值；架构与技术选型合理；接口与数据流完整
- [ ] 任务可执行、依赖明确、风险已识别；验收标准与测试策略完整

**实现验证（implementation）——提交测试前**
- [ ] 实现覆盖全部计划任务；测试全通过（正向/异常/边界）；验收标准逐条满足
- [ ] 无遗留 TODO / 临时绕过；文档与实现一致

**交付验证（deployment）——收尾**
- [ ] 部署/集成已验证；回滚方案可用；meta.yaml 已置 done；变更已记录

## 重要说明

**DO:**
- ✅ 每个关键阶段完成后执行门禁；实现后跑实现验证
- ✅ 手动确认项逐条完成再进下一阶段；质量问题记录到需求文档

**DON'T:**
- ❌ 跳过门禁 / 忽略阻塞性问题
- ❌ 检查未通过就进下一阶段 / 伪造手动确认

## 相关命令

- `/crs:req` — 创建需求（阶段 3 自动触发质量检查）
- `/crs:req-change` — 变更管理（变更后自动触发 Gate 4）
