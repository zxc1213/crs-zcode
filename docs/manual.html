CRS · 智能需求管理系统

为 ZCode 打造：从一个想法到测试完成，全程文档先行、经验复利。
5 阶段文档流程 阶段守卫 Hook 复盘经验沉淀 单入口 /crs:req

CRS 解决什么问题

AI 编程时代最常见的失控是：想法还没说清，代码已经写完了。CRS 在你和代码之间加了一道"文档先行"的流程闸门——需求先被澄清、分析、排期、设计测试，然后才允许动代码。做完还要复盘，经验自动沉淀给下一次。

🧭
一个入口

只需记住 /crs:req。不带参数进入引导模式，带描述自动识别类型并确认。

🚧
阶段守卫

需求还在规划阶段就改代码？Hook 自动注入违规警告，文档先行不打折。

🌱
越用越懂项目

每次需求完成的复盘会沉淀为 lessons，之后创建相关需求自动召回。

📄
纯 Markdown

所有数据是 .requirements/ 下的 Markdown + YAML，任何工具可读，无锁定。

30 秒理解工作方式

你说：/crs:req 添加用户登录功能
系统识别类型 → 确认 → 走 5 阶段文档流程（分析/优先级/测试/计划全部落盘）
你说：开始实现 → 按 plan.md 写代码（此刻起守卫解除）
做完验收 → 说：复盘 FEAT-xxx → 经验沉淀，需求关闭
阅读建议 新用户按顺序读「安装与更新 → 快速上手 → 五阶段流程」即可开始使用；遇到具体问题查「场景手册」和「FAQ」；「架构说明」面向想改代码的维护者。

安装与更新

安装插件

crs-zcode 仓库同时是插件市场（单仓库模式），在 ZCode 客户端中操作：

添加市场

打开 设置 → 插件管理，在「发现」页点 +，输入：

zxc1213/crs-zcode
安装插件

在发现页找到 crs 卡片，点「安装」。新装插件默认启用。

验证

任意会话输入 /crs:req（不带参数）——出现引导界面即安装成功。

更新插件

更新检测靠版本号对比。插件详情页的更新入口只在有新版本时出现——你刚装好时（本地与远程同为 1.0.0）看不到它是正常的。

场景操作
远程发布了新版本详情页底部出现更新入口，或收到更新提醒（客户端 v3.11.2+），点击即可
没有看到更新入口① 确认远程版本确实更高（GitHub 仓库查看 manifest 版本）
② 客户端较旧时：卸载后到「发现」页重新安装，效果等同

维护者发版流程

# 1. bump 版本（package.json）
npm version patch

# 2. 同步版本号到 plugin.json 与 marketplace.json
npm run sync-version

# 3. 提交推送 → 用户端"检查更新"即可拉到
git commit -am "chore: release v1.0.1" && git push
注意 git 型插件的更新检测依赖 manifest 版本号。只 push 代码不 bump 版本，客户端不会提示更新。

快速上手

第一条命令

任意项目会话中输入：

/crs:req

不带参数就是引导模式：显示项目状态概览（几个需求、各在什么阶段）和推荐动作。不用背任何命令，跟着推荐走即可。

创建第一个需求

描述需求

直接输入描述，例如 /crs:req 添加用户登录功能。不需要记 --bug、--refactor 这些选项——系统自动识别类型并和你确认：

📋 识别为「Bug 修复」（将存入 bugs/，ID 前缀 BUG）
   ▶ 直接回车确认开始
   a. 改为调整类    r. 改为重构类    q. 快速模式
等待 5 阶段文档完成

系统自动依次完成：需求解析 → 深度分析 → 优先级评估 → 测试策略 → 实施计划。每阶段结果都会写入文件，你会看到明确的落盘确认。

开始实现

文档就绪后系统会提示。你只需说：开始实现 FEAT-xxx，按 plan.md 执行。

验收并复盘

实现完成说 复盘 FEAT-xxx：生成 retro.md、提炼经验教训到 lessons、关闭需求。

三个最常用的变体

输入适合
/crs:req --quick 修复按钮颜色10 分钟内能搞定的小改动：只建骨架，跳过深度分析
/crs:req --dashboard看全局：统计、活跃需求、最近动态
/crs:req --list列出所有需求及状态
首次使用发生了什么？ 项目还没有 .requirements/ 目录时，创建需求会自动初始化全部目录结构并告诉你创建了什么。无需手动运行任何初始化命令。

五阶段流程

这是 CRS 的核心约束：5 个文档阶段全部完成之前，不修改任何项目代码。每个阶段的结果必须写入文件（不是"输出在对话里"）。

[1/5] 需求解析 + 初始化

经验检索（自动查历史 lessons）→ 安全检查（敏感信息）→ 相似需求检测 → 创建需求目录与骨架文件（meta.yaml、spec/、test-cases/、plan/）。

[2/5] 深度分析

req-brainstorm 方法论：问题探索 → 方案审查 → 设计展示 → 最终审查。产出写入 spec/ 的 5 个文件（背景、用户故事、设计、接口、决策）。

[3/5] 优先级 + 质量检查

按五维加权评估：业务价值 40% · 紧急 30% · 依赖 15% · 成本 10% · 风险 5%。结果写入 meta.yaml。

[4/5] 测试策略

生成正向 / 异常 / 边界三类用例，写入 test-cases/。

[5/5] 实施计划

任务分解 + 里程碑写入 plan/。完成后提示"文档就绪，可以开始实现"。

阶段守卫如何工作

活跃需求处于 planning 或 analyzed 状态时，PostToolUse Hook 检查每次 Edit/Write：

  • 写入 .requirements/ 内 → 放行（这是你该干的事）
  • 写入项目代码 → 注入阶段违规警告，提醒先完成文档流程

状态进入 implementing 后守卫自动解除。

执行模式

模式行为适合
默认走完 5 阶段，给出下一步建议绝大多数需求
--quick只建骨架，跳过分析小改动、急修
--auto文档后自动开始实现方向明确的任务
--conservative每阶段确认后继续高风险/学习模式

命令参考

只有 5 个命令。深度分析、测试策略、文档格式等能力作为 skills 在流程内自动协作，无需手动调用。

/crs:req

主入口。不带参数 = 引导模式（状态概览 + 推荐动作）；带描述 = 创建需求；支持查询选项 --list / --active / --dashboard / --status。

/crs:req-quality

质量门禁 + 验收。--gate 1-4 跑对应阶段门禁（设计/测试策略/计划/变更）；--verify implementation 跑人工验收清单。

/crs:req-priority

优先级。--list 全量排序；跟需求 ID 重新评估单个需求。

/crs:req-change

变更管理。实现中途要改需求时使用：影响评估 → 更新 spec/plan → 自动触发 Gate 4 变更检查。

/crs:metrics

度量分析。吞吐、状态分布、质量数据收集与导出。

/crs:req 选项速查

选项说明
--feature/-f · --bug/-b · --question/-q · --adjust/-a · --refactor/-r显式指定类型（不给则自动识别并确认）
--quick只建骨架，跳过深度分析
--auto / --conservative全自动 / 每步确认
--list · --active · --status <id> · --dashboard查询
复盘 <id>（对话指令）完成复盘并关闭需求

CLI 工具（Bash 可用）

# 相似需求搜索 / 知识图谱统计
node "$ZCODE_PLUGIN_ROOT/bin/kg-cli.js" search "用户登录" 10
node "$ZCODE_PLUGIN_ROOT/bin/kg-cli.js" stats

数据与状态

数据目录

your-project/
└─ .requirements/  # 需求数据（项目本地，可提交 git）
    ├─ features/ bugs/ questions/ adjustments/ refactorings/
    │   └─ FEAT-20260908-001-abc/  # 一个需求一个目录
    │      ├─ meta.yaml  # 元数据：状态、优先级
    │      ├─ raw.md  # 原始描述
    │      ├─ spec.md + spec/  # 设计（5 子文件）
    │      ├─ test-cases.md + test-cases/  # 用例（3 子文件）
    │      ├─ plan.md + plan/  # 计划（2 子文件）
    │      ├─ retro.md  # 复盘（done 时生成）
    │      └─ execution.log  # Hook 自动记录
    └─ _system/lessons/  # 经验库（成长机制）

需求状态生命周期

状态含义此时能否改代码
planning文档阶段（1-2）❌ 守卫警告
analyzed分析完成，文档阶段（3-5）❌ 守卫警告
implementing实现中✅
review验收/复盘✅
done已关闭—

索引文件的设计

spec.md / test-cases.md / plan.md 是摘要索引：根文件记录子文件清单和「待填充/已填充」状态。阶段完成标准 = 三张索引表全部「已填充」。这让任何人（或 LLM）打开需求目录 10 秒内看清进度。

自动化 Hooks

装上插件即生效，无需配置。协议：stdin 读 JSON 事件 → stdout 输出 additionalContext 注入会话。

时机脚本行为
SessionStart
会话启动		session-start.mjs项目有活跃需求时，自动注入需求 ID 和状态提醒（如"FEAT-xxx 还在 planning，先完成文档"）
PostToolUse
每次 Edit/Write/Bash		post-tool-use.mjs① 记录 execution.log
② planning/analyzed 阶段改外部代码 → 阶段违规警告
Stop
会话结束		stop.mjs同步索引表与 plan 进度，输出本次会话执行摘要

活跃需求如何判定

扫描 .requirements/*/*/meta.yaml，取状态 ∈ {planning, analyzed, implementing, review} 中创建时间最新的需求。不依赖符号链接，Windows / macOS / Linux 行为一致。

手动冒烟测试 
printf '{"hook_event_name":"SessionStart","cwd":"<项目路径>"}' \
  | node "$ZCODE_PLUGIN_ROOT/hooks/session-start.mjs"

成长机制

CRS 不只是记录需求——它让经验在项目内复利累积。

经验复利闭环

需求 done 前 → 引导填写 retro.md（估时 vs 实际 / 踩坑与解决 / 可复用结论）
提炼通用教训 → _system/lessons/<topic>.md（带 tags 标注适用领域）
下次创建相关需求时（阶段 1）→ 自动检索相关 lessons 注入分析上下文

lesson 文件格式

---
tags: [登录, jwt, 安全]
source: FEAT-20260908-001
date: 2026-09-08
---
JWT 不要放 localStorage（XSS 可窃取），改用 httpOnly cookie。
适用：所有涉及前端 token 存储的需求。

为什么这样设计

  • 不依赖记忆：经验落盘在项目里，换个会话、换个 LLM 都在
  • 检索而非全量注入：按 tags 相关性召回，不浪费上下文
  • retro 是漏斗：不是所有复盘内容都值得留，提炼环节保证 lessons 库信噪比

跨项目共享（~/.crs/lessons/）规划于 v1.3，见路线图。

场景手册

场景 1：小改动，不想走全流程

/crs:req --quick 修复按钮颜色

只生成骨架直接实现。适合 10 分钟内能完成的改动。

场景 2：实现中途需求变了

/crs:req-change FEAT-20260908-001 改为支持手机号登录

自动评估影响 → 更新 spec 与 plan → 触发 Gate 4 变更检查 → 你继续实现。

场景 3：几个需求先做哪个

/crs:req-priority --list

按五维评分排序，直接给决策依据。

场景 4：实现完了怎么收尾

/crs:req-quality FEAT-20260908-001 --verify implementation   # 人工验收清单

逐项确认后说 复盘 FEAT-20260908-001 → retro + lessons + 关闭，一气呵成。

场景 5：想看整体进度 / 汇报

/crs:req --dashboard                                          # 会话内仪表板
node "$ZCODE_PLUGIN_ROOT/bin/crs-export.js" -o report.html    # 单文件 HTML 报告

场景 6：旧项目直接用

不需要任何预处理。直接 /crs:req，首次创建需求时自动初始化目录。旧需求（如果原来用 Claude 版 CRS 管理）可手动把目录拷进 .requirements/ 对应类型目录下。

常见问题

装好后输入 /crs:req 没反应？

检查三点：① 插件已安装且启用（设置 → 插件管理 → 已安装）；② 会话里输入 / 看命令列表是否有 crs 前缀的命令；③ 重启会话让组件加载。

为什么我没看到"检查更新"按钮？

更新入口只在新版本可用时出现。刚装好时本地与远程版本一致（1.0.0），没有按钮是正常的。等仓库发布更高版本后，详情页底部会出现更新入口（客户端 v3.11.2+ 还会有提醒）。客户端较旧时，卸载后到发现页重新安装等效。

阶段守卫一直警告，我想先改代码？

把 meta.yaml 的 status 改为 implementing 即可解除；或者用 --quick 从一开始就跳过深度流程。守卫的目的是让你有意识地跳过，而不是无意间绕过。

.requirements/ 要提交到 git 吗？

建议提交。它是纯 Markdown + YAML，团队共享需求上下文；execution.log 和临时文件可以在 .gitignore 里排除。

和其他 AI 工具（Claude Code 等）共用项目冲突吗？

不冲突。数据是纯文本，任何工具可读。原 Claude 版 CRS 管理的历史需求目录可以直接拷入对应类型目录继续使用。

lessons 越积越多会不会污染上下文？

召回是按 tags 相关性筛选的，只注入与当前需求相关的少数几条。保持每个 lesson 聚焦一个主题、tags 准确，信噪比就有保障。

怎么彻底卸载？

设置 → 插件管理 → 已安装 → crs → 卸载。项目数据 .requirements/ 完全保留在项目里，不受影响；不需要时手动删除即可。

架构说明

四层模型

用户入口层  commands/（5 个命令，用户显式调用）
智能协作层  skills/（8 个 skill，LLM 按需读取的流程指令）
核心引擎层  scripts/（纯 Node ESM，平台无关，不依赖 skills）
自动守护层  hooks/（ZCode 生命周期钩子）
关键解耦引擎调度的是 ZCode 通用 skills（brainstorming / writing-plans 等），不依赖任何 req-* skill——调整 skills/commands 不影响引擎，反之亦然。

引擎模块

模块职责
requirement-manager/core/processor.js需求创建 / 状态机 / 骨架生成 / 模板渲染
requirement-manager/core/scheduler.js执行计划与 skill 调用链
requirement-manager/core/router.js意图识别与路由
requirement-manager/features/安全过滤、相似度检测
requirement-manager/utils/plan-sync.jsplan 进度与 meta.yaml 状态同步
knowledge-graph/Fuse.js 相似需求搜索
export/ · metrics/HTML 报告导出 · 度量收集

项原版本版

演进路线

原则：每个版本一个主题；每项改动有测试保护；体验优先于功能数量。

v1.1 引导与成长 当前

  • ✅ /crs:req 引导模式与对话式类型确认
  • ✅ 复盘机制（retro.md）+ lessons 沉淀与自动召回
  • ✅ 死代码清理（optimization/ ~1300 行、conversation-logger/、demo.js）

v1.2 引擎重构

  • processor.js（553 行）拆分为模板渲染 / 创建 / 状态机三模块
  • scheduler 去 Claude 时代 adapter 遗产，只管阶段顺序
  • 项目级配置：.requirements/_system/config.yaml（优先级权重、门禁阈值）
  • 验收标准：核心链路任一环节，新维护者 10 分钟定位到代码

v1.3 生态与反馈

  • metrics 迭代视图：吞吐量、返工率、估时准确度
  • 复盘数据驱动：估时偏差回写优先级权重建议
  • 跨项目 lessons 库（~/.crs/lessons/）

反模式（明确不做）

  • ❌ 重新支持多平台
  • ❌ 命令数量超过 5 个
  • ❌ 引入数据库 / 运行时配置 UI —— Markdown + YAML 是数据底线
